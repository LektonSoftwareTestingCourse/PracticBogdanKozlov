## 2. Бизнес-отказы

Внутренние статусы сверены с [AuthControllerImpl](../../services/authorization/src/main/java/com/processing/authorization/controller/AuthControllerImpl.java) и [DeclineOutcome](../../services/authorization/src/main/java/com/processing/authorization/constants/DeclineOutcome.java). Проверки сопоставляют ISO-код и причину, а у операций с деньгами также проверяют баланс, где он наблюдаем через API.

| Исход | Код и причина | Путь и подготовка |
|---|---|---|
| Карта не найдена | `14 CARD_NOT_FOUND` | Отсутствующий PAN с известным BIN, удалённая карта, неизвестный BIN в Switch, HTTP 400 или 404 на шаге reserve |
| Заблокирована | `05 CARD_BLOCKED` | PATCH статуса на BLOCKED, ответ HTTP 402 при чтении карты в управляемой зависимости |
| Неактивна | `05 CARD_INACTIVE` | PATCH статуса на INACTIVE |
| Просрочена | `54 CARD_EXPIRED` | PATCH статуса на EXPIRED. Отдельный тест оставляет карту ACTIVE и проверяет запрос в последний день срока и на следующий день |
| Недостаток средств | `51 INSUFFICIENT_FUNDS` | Баланс на одну копейку меньше суммы, отдельный ответ HTTP 402 на входе reserve |
| Превышение лимита | `61 EXCEEDS_AMOUNT_LIMIT` | Вторая операция превышает дневной лимит в тот же день или месячный лимит в другой день месяца |
| Карточный сервис недоступен | `96 SERVICE_UNAVAILABLE` | Отказ соединения при чтении или откате, отдельно HTTP 503 при резервировании |
| Ошибка резервирования | `96 RESERVATION_FAILED` | Card Management отвечает HTTP 409 на резервирование в управляемой зависимости |
| Неизвестная причина | `05 UNKNOWN_REASON` | Управляемый ответ карточного сервиса с `status: null` |
| Резерв для отката отсутствует | `14 TRANSACTION_NOT_FOUND` | Запрос с новым RRN, отдельно HTTP 400 на rollback у зависимости |
| Резерв уже возвращён | `05 ALREADY_ROLLED_BACK` | Успешная авторизация, два запроса на откат одного RRN |
| Ошибка отката | `96 ROLLBACK_FAILED` | Управляемый HTTP 422 на rollback у зависимости |
| Ошибка публикации | `96 System error` | Приложение RabbitMQ остановлено в работающем контейнере, чтобы сохранить DNS. Gateway возвращает отказ, баланс восстановлен и записи с этим STAN нет в течение окна наблюдения |

## 4. Расхождения контракта и реализации

| Декларировано или ожидается | Наблюдается | Источник и классификация |
|---|---|---|
| MTI ответа авторизации `0110` | Успешный ответ содержит `0100` | [API-спецификация](../api-spec.md#authorizationresponse) и `AuthorizationResponse.approved`. Дефект контракта ответа. Проверка воспроизведения сохраняет ожидание `0110` |
| Каталог мерчантов опубликован в OpenAPI с адресом Gateway | У Gateway этот путь отдаёт 404, прямой сервис возвращает 200 | [OpenAPI](../api/openapi.yaml) и конфигурация маршрута `/api/simulator/merchant/**`. Дефект маршрутизации. Потребитель по опубликованному адресу не получает каталог |
| Неверный диапазон должен сообщить, какое правило нарушено | Поиск и charts дают 400, при этом `message` пустой | Валидаторы диапазона и `GlobalExceptionHandler` Logger. Дефект диагностики. Обработчик агрегирует ошибки полей, а валидатор выдаёт ошибку объекта |
| В примере карты срок задан как `MMYY` | В ответе создание и чтение возвращают `YYYY-MM` | [API-спецификация](../api-spec.md#2-cards-card-management-service), DTO `CardModel` и наблюдение в HTTP. Расхождение формата документации и реализации, значимое для парсинга |
| Поиск описывает шесть фильтров в Markdown | Также работают `issuerId` и `mcc` из `TransactionFilter`. STAN отбирается в теле ответа по GPath | [Markdown-спецификация](../api-spec.md#3-transactions), контроллер Logger и реализация фильтрации. Неполная документация Markdown. Ожидания для дополнительных фильтров подкреплены контроллером и запросами |
| В OpenAPI указаны terminal `/start` и `/status` | Контроллер реализует `/start-continuous` и `/stop` | [OpenAPI](../api/openapi.yaml) и `TerminalSimulatorController`. Расхождение перечня маршрутов, для работающих маршрутов есть тесты |
| Для дубликата PAN при создании карты указан HTTP 409 | `CreateCardRequest` принимает BIN и атрибуты карты, сервер генерирует PAN самостоятельно | [API-спецификация](../api-spec.md#2-cards-card-management-service) и DTO. Ограничение интерфейса: публичный клиент не может детерминированно запросить создание того же PAN |
| Gateway должен возвращать 503 при недоступном downstream | При остановленном Switch один прогон дал 500 на POST транзакции. Проверка 503 изолирует отказ соединения с доступным DNS и закрытым портом | [OpenAPI](../api/openapi.yaml) и `DownstreamExceptionUtils`. Дефект маскировки инфраструктурной ошибки. Разные виды недоступности дают разные ответы |
| `DeclineOutcome` предусматривает доменную причину `DB_UNAVAILABLE` при отказе обновления лимитов | В отдельном HTTP-эксперименте с остановленной PostgreSQL Authorization вернул общий 500 без доменного кода. Поиск Logger также вернул общий 500 | `AuthServiceImpl`, `DeclineOutcome` и HTTP-прогон. Остановка всей БД не позволяет изолировать момент вызова upsert. Внешний клиент получает общую ошибку |

Первые три расхождения воспроизводятся в `KnownDiscrepanciesTest` с обычными проверками ожидаемого контракта. Их можно запустить через группу `known-discrepancy` на штатном стеке. В обычном прогоне соответствующие эндпоинты покрыты по тем частям контракта, которые подтверждены.

## 5. Обоснование достаточности

- **Лекция 9.** Тесты использовали HTTP-статус, содержание JSON, заголовки и схему одновременно. Например, одобрение проверяет `APPROVED`, `00`, STAN, формат RRN и кода авторизации, JSON Schema и резервирование средств по отдельному запросу к Card Management.
- **Лекция 10.** Ошибки формы запроса и отрицательные бизнес-решения имеют отдельные проверки. Идемпотентность проверяется по UUID записи и включает конфликт данных. Для результатов поиска выбран идентификатор собственной записи. Для появления записи и отсутствия записи после отката используются два разных условия Awaitility.
- **Тест-дизайн.** Обязательность, формат и граничные значения дают различимые классы входа. В тестах поиска все 10 параметров включены в 16 попарных комбинаций уровней «передан» и «пропущен». Для любых двух параметров получаются все четыре сочетания. Отдельные проверки делают запросы с не совпадающими значениями фильтров и проверяют, что созданная запись исключена.
- **Изоляция.** PAN возвращает API создания карты или определяет фабрика для отсутствующей карты. STAN, RRN и UUID генерируются на тест. Тесты меняют состояние через HTTP. Docker поднимает отдельный проект с чистым томом и портами на loopback. Управляемая зависимость используется для исходов Card Management, которые нельзя надёжно получить на реальном сервисе через публичный API.
- **Оставшиеся риски.** Полный каталог ответов 5xx при внутренних исключениях и `DB_UNAVAILABLE` при отказе операции upsert в Authorization требуют дополнительных точек инъекции. Валидация управления стендом, WebSocket, содержимое БД и доставка сообщения в самом RabbitMQ относятся к другим уровням тестирования. Для Swagger UI автоматизирован только HTTP-контракт входной страницы и OpenAPI-прокси.

## 7. Порядок запуска

Требуются JDK 21, Maven, Bash, jq и Docker с Compose. Из корня проекта:

```bash
bash scripts/api-tests.sh
```

Скрипт собирает образы, поднимает отдельный стек, выполняет основные тесты и сценарии остановки зависимостей, проверки rate limit и управляемых ответов Card Management. В конце он удаляет созданный стек и его том. Для трёх подряд прогонов штатного набора:

```bash
API_TEST_REPEATS=3 bash scripts/api-tests.sh
```

Если стек уже поднят на стандартных портах, штатные HTTP-тесты запускаются отдельно:

```bash
mvn -B -ntp -f services/pom.xml -Papi-tests test
```

Известные расхождения можно воспроизвести на том же поднятом стеке:

```bash
mvn -B -ntp -f services/pom.xml -Papi-tests -Dapi.test.groups=known-discrepancy test
```

[Workflow GitHub Actions](../../.github/workflows/api-tests.yml) автоматически запускает тот же скрипт и публикует отчёты Surefire. Для локального запуска с нестандартными портами Maven принимает `-Dapi.gateway.url=...`, `-Dapi.cards.url=...` и аналогичные свойства из `Api.java`. Скрипт Compose подставляет их сам.
