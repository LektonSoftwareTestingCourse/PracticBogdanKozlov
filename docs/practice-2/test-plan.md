# Тестовый план СМП

## 1. Область и подход

План охватывает подготовку артефакта 2 для всей СМП: стратегию, план, test-design ядра и чек-листы. Объект тестирования — микросервисная система из Gateway, Card Management, Switch, Authorization, Terminal Simulator, Merchant Simulator, Transaction Logger, Bin Lookup, Notification Service, Web Dashboard, PostgreSQL и RabbitMQ.

Подход: чёрный ящик по требованиям и API-контрактам. Для Authorization и Card Management выполняется глубокое проектирование тестов по техникам лекции 3: классы эквивалентности, граничные значения и pairwise. Для остальных сервисов готовятся чек-листы дымового тестирования и критического пути. Основной источник требований — `tz/04-authorization.md`, `tz/05-card-management.md`, `docs/architecture.md`, `docs/api-spec.md` и `docs/checklists.md`.

## 2. Критерии входа и выхода

**Критерии входа:**

- доступны требования по Authorization и Card Management;
- известны обязательные endpoints Gateway, Card Management, Authorization, Simulator и Dashboard;
- определён состав артефакта 2 и пути файлов в `docs/practice-2/`;
- модель pairwise содержит не менее шести параметров и ограничения.

**Критерии выхода:**

- созданы четыре документа: `test-strategy.md`, `test-plan.md`, `test-design.md`, `checklists.md`;
- созданы `docs/practice-2/pict/model.txt` и `docs/practice-2/pict/cases.txt`;
- в `test-design.md` есть классы эквивалентности, граничные значения, pairwise и тест-кейсы;
- каждый тест-кейс содержит ID, требование, источник, предусловие, шаги и ожидаемый результат;
- строки `cases.txt` спроецированы в тест-кейсы;
- в артефакт не включены таблицы решений, переходы состояний и баг-репорты.

**Критерии приостановки и возобновления:**

- работа приостанавливается, если отсутствует доступ к требованиям ядра или найдено противоречие, из-за которого невозможно определить ожидаемый результат;
- работа возобновляется после уточнения требования или явного фиксирования допущения в документе.

## 3. Ресурсы и расписание

| Этап | Содержание | Результат |
|---|---|---|
| Анализ документации | Лекция 3, шаблон артефакта, практика 2, ТЗ Authorization/Card Management, архитектура, API и чек-листы | Список требований, классов и границ |
| Проектный слой | Стратегия и план на всю СМП | `test-strategy.md`, `test-plan.md` |
| Ядро | КЭ, ГЗ, pairwise и тест-кейсы для Authorization и Card Management | `test-design.md`, `pict/model.txt`, `pict/cases.txt` |
| Периферия | Дымовой и критический чек-листы | `checklists.md` |
| Самопроверка | Проверка структуры, техники и состава артефакта | Готовность к сдаче через Issue |

Ресурсы: один тестировщик, требования в репозитории, Markdown-документы, PICT-совместимая модель pairwise. Если PICT недоступен локально, допускается резервная генерация pairwise-набора без изменения состава артефакта: итоговые `model.txt` и `cases.txt` должны быть сохранены в репозитории.

## 4. Риски

| Риск | Влияние | Снижение |
|---|---|---|
| Смешивание техник лекций 3 и 4 | Артефакт не соответствует заданию | Не включать таблицы решений, state transition и баг-репорты |
| Документы описывают только один сервис | Потеря проектного слоя стратегии и плана | Стратегию и план писать на всю СМП |
| Модель pairwise содержит невозможные сочетания | Набор непригоден для тест-кейсов | Добавить constraints для статуса карты, expiry и доступности CMS |
| Несколько невалидных значений в одном кейсе | Причина отказа не локализуется | Один невалидный класс — один тест |
| Неоднозначность responseCode месячного лимита | Разный результат у реализаций | Принять допущение: месячный лимит отклоняется как limit exceeded, `responseCode="61"` |
| Асинхронная запись в Logger видна не сразу | Ложный отрицательный результат в критическом пути | Проверять наличие транзакции с учётом eventual consistency |
